- (decision) [ADOPTED] Thin-router / domain-service pattern already in use (services/preferences.py, services/sources.py): routers take a Session + validated schema, delegate to a pure service function; services own get-or-create idempotency and business rules, raise ValueError on bad input which routers translate to HTTPException. New Taxonomy/Suggestion code follows this shape -- no new layering pattern introduced.
- (decision) [ADOPTED] Admin review-queue pattern already in use (Source.status: pending/approved/rejected as a plain string column, no enum/constraint; services/sources.py:set_source_status; admin.py: GET list-pending + PATCH update-status under require_admin). The new Taxonomy Curation Queue (PendingTaxonomySuggestion) reuses this exact status shape rather than inventing a new review-state pattern.
- (decision) [ADOPTED] Pluggable-provider pattern already in use for LLM access (llm/base.py: ABC with template-method retry, llm/types.py: frozen dataclass contract objects speaking domain language not provider language, llm/factory.py: dict-keyed-by-settings-string factory, config.py: one NEWSAGENT_<X>_PROVIDER-shaped setting per pluggable system). The PRD's 'Suggestion Source' pluggable interface is architected as a sibling package (newsagent/suggestions/) mirroring this exact shape -- new ABC, new typed contract, new factory, new NEWSAGENT_SUGGESTION_PROVIDER setting -- deliberately NOT reusing llm_provider/LLMProvider, since the PRD requires the suggestion-source model to be a separate deployment from the article-generation LLM. MVP ships a 'popularity' adapter (no LLM call); the future LLM-backed adapter is a later addition behind the same interface.
- (decision) [ADOPTED] No migration tool is wired into the project today (Alembic is an installed dependency but no alembic/ directory or migration convention exists in-repo; schema setup is ad-hoc/create_all-style). Flagged as a real open question below rather than silently assumed -- this feature adds 4+ new tables/columns, which is exactly the kind of change that diverges badly if two people each hand-rig their own migration approach.
- (decision) Async suggestion computation runs as a FastAPI BackgroundTask fired after the profile save, in-process -- not piggybacked on the scheduled pipeline, no task queue introduced. Accepted tradeoff: lost on crash/restart, no retry beyond what the provider adapter itself does (mirrors llm/base.py's own retry-then-typed-error contract).
- (decision) User profile fields (field_id, role_id, role_other_text, experience_bucket, interest_free_text) live as direct columns on User, not a separate UserProfile table, per explicit user preference -- 'keep it simple for now, may change later.' Documented as a real, revisitable call, not an oversight.
- (decision) Consequence of the BackgroundTask choice: the PUT that saves the profile returns before suggestions are computed, so the frontend needs a way to fetch suggestion state afterward. Resolution: two more columns on User -- suggestion_status (none/pending/ready/failed) and suggested_topic_ids (JSON list) -- plus a new GET /me/topic-suggestions endpoint the frontend polls after save until status is ready or failed. Keeps the same 'flat on User for now' shape the user just chose for profile fields.
- (decision) PendingTaxonomySuggestion table: one row per unique (kind: field|role, field_id nullable for kind=field, normalized_text), upserted with an incrementing submission_count -- matches the existing get-or-create idiom (add_topic/add_source in services/sources.py) rather than one-row-per-submission plus a query-time GROUP BY.
- (decision) 4-Topic hard cap (PRD FR-10) enforced inside the existing shared services/preferences.py:set_preferences -- the single existing mutation point for UserTopicPreference -- so it applies platform-wide to every caller (old raw toggle grid included), per the PRD's explicit 'platform-wide, not suggestion-scoped' wording.
- (decision) New admin_taxonomy.py router (mirrors admin.py's shape: require_admin dependency, GET list-pending + PATCH-style promote/dismiss) rather than extending admin.py directly -- keeps source-approval and taxonomy-approval as separate concerns at the same granularity as the existing router split (auth.py/me.py/tracking.py/admin.py).
- (convention) Frontend chip/pill/segmented-control components for this feature must be real semantic elements (<button> with aria-pressed, or native radio/checkbox inputs), never <div onclick=...> -- the UX mockup's div-based pattern was an explicit shortcut, not an approved pattern (tracked as news-agent#31). Two independently-built components diverging on this is exactly the kind of accessibility regression this convention prevents.
