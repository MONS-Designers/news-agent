- (note) Created from GitHub issue #60 (news-agent repo, 'Expand the topic pool beyond the three seeded topics') plus a full requirements negotiation with the user (Nomi) across a live conversation; headless invocation (caller pre-supplied all inputs and an output path), express distill, no elicitation; slug topic-source-discovery
- (note) Adopted companions identified during drafting: spec-llm-provider-interface (this feature adds a new method to that same LLMProvider contract) and spec-topic-suggestions (this feature's trigger point is the exact Topic-creation path that spec already specified); both referenced, not duplicated
- (decision) User decided to eliminate DEFAULT_SOURCES and seed_default_sources() entirely (services/sources.py) - the DB, populated by an automated discovery job, becomes the only source of truth for Topic-to-Source mappings; no code-defined source list may remain as a competing authority
- (decision) Exactly one LLM call (a 'finder') discovers RSS candidates per topic. User explicitly rejected adding a second, independent 'judge' LLM for this feature - deferred to the future multi-stage pipeline overhaul already noted as an open item in CLAUDE.md; the deferral is to be documented as a code TODO plus a CLAUDE.md update, not built now
- (decision) New pending Topics already arise from one single code path today: services/preferences.py::set_preferences's new_topic_names resolution - reached both when a user hand-types an interest and when a user picks an LLM-invented suggestion from the separately-specified Step 3 flow (spec-topic-suggestions). This spec's trigger point is exactly that path; no new topic-creation entrypoint is introduced
- (decision) Search criteria for the finder LLM, the user's own words: a source must be authoritative/credible, of global scale, free (no paywall behind it), and on-topic
- (decision) Candidate validation is deterministic, never LLM-judged: each candidate URL is actually fetched and parsed (feedparser, the same library pipeline/fetcher.py already uses) before it may become a Source row, specifically to catch a hallucinated or dead URL the finder LLM proposed
- (decision) Discovery runs as a background job triggered once, at Topic-creation time - not a periodic batch sweep. Asked the user which was better; agreed with the recommendation against adding speculative retry/sweep complexity for V1, so a topic where the first attempt finds zero sources stays sourceless until reconsidered later
- (decision) Topic color is generated automatically per topic, not chosen from any fixed/enumerated palette: a candidate color is checked for uniqueness against every other Topic.color already stored, and for WCAG AA 4.5:1 contrast against the digest email's #0b1020 background, retried until both checks pass
- (decision) User confirmed pending-source articles must reach only the digest of users actually subscribed to that specific topic. Achieved by extending the existing Source.status filter - already scoped by subscribed_topic_ids in both pipeline/fetcher.py and pipeline/relevance.py - from approved-only to approved-or-pending; no new per-user visibility mechanism is introduced
- (capability) CAP-1 A newly created pending Topic (from either new-topic-name path in services/preferences.py::set_preferences) automatically gains real, working RSS sources with no code change, seed edit, or admin action. Success: creating a new Topic through the existing flow results, without further human input, in one or more Source rows under it whose feed URL is independently confirmed reachable and parseable
- (capability) CAP-2 Every Topic carries a color that is unique across all Topics and legible against the digest's dark background, without anyone hand-assigning it. Success: for any Topic old or new, Topic.color is set, no two Topic rows share the same value, and every one independently measures at or above 4.5:1 contrast against #0b1020
- (capability) CAP-3 A reader who just subscribed to a brand-new topic sees articles from that topic's newly-discovered sources in their own digest before any admin has reviewed those sources - discovery is not gated on manual curation. Success: subscribe a user to a new topic, let discovery complete, run the fetch/relevance/digest pipeline; that user's digest includes articles from the new sources while a second user not subscribed to that topic sees none of them
- (capability) CAP-4 Creating a Topic never makes the triggering request wait on source discovery. Success: the preferences-save request completes on its own existing timing; Source rows for the new topic appear afterward with no second user action required to fetch them
- (capability) CAP-5 A source candidate that does not actually resolve to a working feed is rejected before it can become a Source row, regardless of how plausible the finder LLM made it look. Success: given a candidate list containing one genuinely reachable feed and one dead or fabricated URL, only the reachable one is persisted
- (constraint) discover_sources joins llm/base.py's existing template-method contract, the same shape as score_relevance/summarize (public wrapper + abstract adapter method, retried the same way) - speaks domain language (topic, source, feed) not prompt/token language, matching spec-llm-provider-interface's existing constraint on that contract
- (constraint) Source-candidate validation is deterministic (an actual feed fetch+parse), never delegated to LLM judgment - this feature ships with no second/independent LLM verifying candidates
- (constraint) No hardcoded source list may remain as a competing source of truth once this ships: DEFAULT_SOURCES, seed_default_sources(), SeedReport, and the seed-sources CLI command are removed, not merely unused
- (constraint) Topic.color is computed fresh against the live DB state every time (checked against every existing Topic.color row) - never drawn from a fixed/enumerated lookup table, since a hardcoded color map is exactly what is being removed
- (constraint) Pending-source article visibility relies entirely on the pre-existing subscribed_topic_ids scoping already enforced in pipeline/fetcher.py and pipeline/relevance.py - both must change their Source.status filter from approved-only to approved-or-pending, since a shared/batch pipeline stage that still filters to approved-only would never fetch or score a pending source's articles at all, regardless of downstream digest logic
- (constraint) Migration is additive-only: a nullable Topic.color column, plus a backfill of the 3 pre-existing approved Topics (בינה מלאכותית, סייבר, חלל) with their current hardcoded render.py colors, so nothing changes visually for them
- (constraint) Migration content, including the exact backfill values, must be shown to the user for review before it is ever run - standing project rule, applies every time, not a one-off ask for this feature
- (decision) Non-goals: a second/independent LLM judge for source quality (explicitly deferred, see decisions above); any new admin UI to review/approve a pending Topic itself (Source-level approval via the existing admin.py endpoint is unchanged and untouched - a pending Topic having no reviewer of its own is a pre-existing, separately tracked gap, not something this spec closes); any change to how suggest_topics/suggest_new_topics rank or invent topic names (separate mechanism, a production issue with it is tracked as GitHub issue #72); LLM cost/spend control policy for the new discover_sources calls (ownership sits with news-agent-infra per the project's cross-repo split, coordination flagged by the user as a pending prerequisite, not a blocker to writing this spec)
- (assumption) The finder LLM call reuses whatever provider adapter the existing LLMProvider factory (llm/factory.py) already resolves, rather than introducing a second, separate provider-selection axis for this one capability - not explicitly stated by the user, but consistent with the existing architecture and with not adding speculative configurability
- (assumption) No automatic retry or periodic sweep job for a topic where the first discovery attempt finds zero valid sources - a permanently-sourceless pending Topic is an accepted V1 edge case, per the user's agreement to keep this to a single at-creation attempt
- (question) OPEN: which concrete LLM provider/model should serve as the finder, and should it sit behind a feature flag until news-agent-infra (Moshe) has weighed in on the cost of a new, frequent LLM call triggered by ordinary user activity (every new topic, not a controlled batch job)? The user flagged this coordination as unresolved and explicitly separate from writing this spec, but it needs a human decision before this capability is turned on against a real provider in production
- (event) self-validate pass 1 (coherence): PASS - all 5 CAPs carry intent+success; constraints each rule out a concrete alternative (LLM-judged validation, a fixed color palette, approved-only pipeline filters, a surviving hardcoded source list); non-goals explicit (4 items) with the pending-Topic-admin-review gap named as pre-existing rather than silently absorbed; success signal is demonstrable end-to-end; capability IDs unique; prose lean. One open question retained (provider/cost gate) since the input left it genuinely unresolved
- (event) self-validate pass 2 (preservation): PASS - every load-bearing claim from the conversation (trigger point being the shared set_preferences path, the two exact pipeline query locations, the migration backfill requirement, the four search criteria, the deterministic-validation requirement, the color uniqueness+contrast rule, the pending-source visibility scoping, the ask-first migration rule) landed in SPEC.md or the code-map.md / discovery-flow.md companions; no wrapper-only content dropped
- (event) spec finalized
- (decision) 2026-09-06 user resolved the open provider question: V1 uses the already-configured EXTERNAL provider as the finder, no feature flag of its own; a future finder-model change is a provider-config change, not a code change. Open Questions now carries no blocker - only a heads-up to news-agent-infra that discover_sources is triggered by ordinary user activity rather than a controlled batch job
- (event) adversarial review (AR) + edge-case-hunter review (ECH) run against SPEC.md and code-map.md, both validated against the live codebase rather than the spec's own claims. Both independently surfaced the same three: the globally-unique Source.url collision, the request-scoped-Session-into-BackgroundTask prescription, and the breadth of the pending-status pipeline widening. ECH additionally surfaced the non-http scheme gap
- (decision) 2026-09-06 user chose to keep Source-to-Topic one-to-many rather than move to many-to-many. Rationale: Source.topic_id is not ownership metadata - pipeline/relevance.py derives the single topic an Article is scored against via article.source.topic.name, and pipeline/render.py derives the digest label and color the same way. Many-to-many means an Article no longer has one topic, which ripples into per-topic scoring, the single-valued Article.relevance_status column, and digest labeling. Accepted cost, now an explicit non-goal: a feed already owned by one Topic cannot be reused by another. Mitigated by branching on add_source's created flag (logged collision, never counted as success) and by asking the finder for more candidates than the keep-cap
- (decision) 2026-09-06 user chose to replace the seed-sources CLI with discover-topic "<name>" rather than retain any reduced hardcoded seed. Rationale: a reduced seed would be exactly the competing source of truth the spec's own constraint forbids; routing bootstrap through the production discovery path keeps one way sources enter the system, gives docs/v1-manual-test-plan.md a direct replacement line, and makes the background-task feature triggerable without OAuth plus the preferences UI. Works offline via NEWSAGENT_LLM_PROVIDER=mock against the discover_sources double the code-map already requires
- (event) SPEC.md, code-map.md and discovery-flow.md updated with the review findings: http/https scheme check before any fetch, db.get_bind() instead of the request session, Refusal and LLMError both terminal-but-logged, color assigned first and unconditionally with a capped retry loop, unique constraint on topics.color plus a downgrade() and an id-resolved backfill, candidate dedupe/cap/timeout/bozo rejection, Topic.status rejected excluded from the widened pipeline queries, CAP-1 and CAP-2 success criteria reworded to match what the design can actually guarantee, and a new code-map section for the tests and docs the removal breaks
