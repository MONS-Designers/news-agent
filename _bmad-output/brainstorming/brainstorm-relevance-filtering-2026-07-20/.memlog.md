- (technique) started First Principles
- (idea by coach) filtering is fundamentally a persistent verdict on an article-topic pair, not a transient computation - the verdict must outlive the run
- (idea by coach) an article inherits its candidate topic from its source (source.topic_id) - no cross-topic scoring needed in MVP, the pair is fixed at fetch time
- (idea by coach) the stage is a state machine on Article: pending -> relevant | irrelevant | refused | error; each state has different downstream behavior
- (idea by coach) score and verdict are separate: score is provider fact (0-1), verdict is pipeline policy (threshold from config) - store both so threshold changes can re-verdict without re-scoring
- (idea by coach) scoring exactly once per article is the cost model: the DB row IS the cache (purity property from #5 spec)
- (idea by coach) input problem: fetcher stores only title+url; full_text is #9 (not built). MVP filter must work on title alone - or fetcher should also capture the RSS summary/description field
- (idea by coach) RSS entries almost always carry a summary/description - storing it at fetch costs nothing and dramatically improves filter signal vs title alone
- (technique) started Pre-mortem (imagine the filter failed badly in production)
- (idea by coach) postmortem: digest arrived empty for a week - threshold too high for a stingy provider; fix: log score distribution per run so drift is visible
- (idea by coach) postmortem: LLM bill exploded - filter re-scored all 5000 historical articles after a schema migration reset statuses; fix: only score articles in pending state, never re-enter terminal states
- (idea by coach) postmortem: one provider outage marked 200 articles error and they never recovered; fix: error is retryable - next run picks error articles up again (error != terminal)
- (idea by coach) postmortem: great article dropped silently, nobody knew why; fix: verdicts carry the score that produced them - auditable in DB, no black box
- (idea by coach) postmortem: run crashed mid-batch, half scored half not - per-article commit (like fetcher) so progress survives crashes
- (idea by coach) postmortem: filter ran on articles whose source was later rejected - filter only articles from currently-approved sources
- (technique) started Cost Lens (every idea judged in dollars)
- (idea by coach) title+rss-summary is ~50-100 tokens vs full text ~1000+: filtering BEFORE extraction (#9) is 10x cheaper - pipeline order: fetch -> filter -> extract only relevant -> summarize
- (idea by coach) score_relevance_many (batch, built in #5) is the natural call shape - one run scores all pending in one loop, adapter may batch for real later
- (idea by coach) aggregate usage from RelevanceScore.usage into the run report - first real consumer of the usage field, feeds #19 for free
- (idea by coach) refused articles (junk/too short) cost zero LLM calls when refusal check is input-side - mock refuses before scoring; real adapter should too
- (technique) started Role Playing (stakeholder voices, solo)
- (idea by coach) as the DBA: do NOT bloat Article with filter columns forever - but for MVP two columns (relevance_score, relevance_status) beat a join table; revisit only if multi-topic scoring arrives
- (idea by coach) as the future admin UI: irrelevant articles should remain queryable (why was X dropped?) - soft verdicts in DB enable a review screen later, deletion would destroy it
- (idea by coach) as Naomi (pipeline dev): filter stage = one function filter_pending_articles(db, provider) -> FilterReport, symmetric with fetcher; CLI command 'filter'; scheduler later just chains stages
- (idea by coach) as the digest builder (#12, next consumer): give me one boolean question answerable by index - status == relevant - not a score I must interpret
- (idea by coach) as the reader: borderline scores (0.3-0.7 between anchors) worry me - MVP policy: single threshold decides; log borderline count so we can tune with real data
- (technique) started Edge Case Safari (invented: hunt inputs that break the happy path)
- (idea by coach) edge: article with Hebrew title from a Hebrew feed - provider contract handles any language, no special casing in filter
- (idea by coach) edge: same story from two sources (TechCrunch + Verge cover same launch) - both scored independently; cross-source dedup is a different problem, explicitly out of scope for #10
- (idea by coach) edge: topic renamed by admin - scores already stored survive; verdict recomputation is possible because score is kept separate from verdict
- (idea by coach) edge: empty RSS summary stored as empty string vs None - normalize at fetch: absent summary = None, filter builds ArticleInput from title + (summary or '')
- (idea by coach) edge: refused by provider (too short) - status refused, terminal, zero retries; distinct from error which retries
- (technique) started SCAMPER (mutate the stage design)
- (idea by coach) Substitute: LLM scoring for keyword pre-filter? No - but a zero-cost heuristic pre-gate (dead link, duplicate title) could shrink LLM calls later; not MVP
- (idea by coach) Combine: filter+extract in one pass? No - order matters for cost (filter first is 10x cheaper); keep stages separate per architecture
- (idea by coach) Adapt: fetcher's SourceResult/FetchReport reporting pattern adapts directly to FilterReport (scored, relevant, irrelevant, refused, errors, usage_total)
- (idea by coach) Eliminate: no per-topic thresholds in MVP - one global NEWSAGENT_RELEVANCE_THRESHOLD (default 0.7 = the contract anchor); per-topic tuning is speculative
- (idea by coach) Reverse: instead of filter pulling pending articles, digest builder filtering lazily at build time? No - lazy loses the once-per-article cost guarantee and mixes stages
- (insight) synthesis: the stage is a persistent verdict machine - score once (DB row = cache), verdict = policy(score, config threshold), states pending/relevant/irrelevant/refused(terminal)/error(retryable); needs fetcher to also store RSS summary; report mirrors fetcher pattern and aggregates usage; threshold global 0.7 default
