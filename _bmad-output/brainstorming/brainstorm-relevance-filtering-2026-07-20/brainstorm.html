01 · Technique

First Principles

Strip the stage down to what must be true, layer by layer, bedrock up.

the core claim

Filtering is fundamentally a persistent verdict on an article–topic pair, not a transient computation — the verdict must outlive the run.

the pair is fixed

An article inherits its candidate topic from its source (source.topic_id) — no cross-topic scoring needed in MVP; the pair is fixed at fetch time.

it's a state machine

The stage is a state machine on Article: pending → relevant | irrelevant | refused | error; each state drives different downstream behavior.

score ≠ verdict

Score and verdict are separate: score is provider fact (0–1), verdict is pipeline policy (threshold from config) — store both so threshold changes can re-verdict without re-scoring.

the cost model

Scoring exactly once per article is the cost model: the DB row IS the cache — the purity property carried over from the #5 spec.

the input problem

Fetcher currently stores only title + url; full text is #9 and not built yet. MVP filter must work on title alone — or the fetcher should also capture the RSS summary/description field.

the resolution

RSS entries almost always carry a summary/description — storing it at fetch time costs nothing and dramatically improves filter signal versus title alone.

02 · Technique

Pre-mortem

Imagine the filter already failed badly in production. Six case files from the autopsy.

digest arrived empty — for a week

Threshold too high for a stingy provider; nobody noticed the score distribution had drifted.

Log the score distribution every run so drift is visible.

LLM bill exploded

A schema migration reset article statuses; the filter re-scored all 5,000 historical articles in one run.

Only score articles in pending state — never re-enter terminal states.

200 articles stuck forever

One provider outage marked 200 articles error and they never recovered.

error is retryable — next run picks error articles up again (error ≠ terminal).

a great article vanished, silently

Dropped by the filter and nobody could say why — no trace of the decision.

Verdicts carry the score that produced them — auditable in the DB, no black box.

run crashed mid-batch

Half the batch scored, half not, and the crash lost track of which was which.

Per-article commit, same pattern as the fetcher — progress survives crashes.

filtered a rejected source

The filter ran on articles whose source was later rejected by an admin.

Filter only articles from currently-approved sources.

05 · Technique

Edge Case Safari

Invented for this session: hunt the inputs that break the happy path.

#1
non-english title

A Hebrew title from a Hebrew feed — the provider contract handles any language; no special-casing in the filter.

#2
duplicate coverage

Same story from two sources (TechCrunch + Verge cover the same launch) — both scored independently. Cross-source dedup is a different problem, explicitly out of scope for #10.

#3
topic renamed mid-flight

Topic renamed by an admin — scores already stored survive; verdict recomputation is possible because score is kept separate from verdict.

#4
empty summary ambiguity

Empty RSS summary stored as empty string vs None — normalize at fetch: absent summary = None; filter builds ArticleInput from title + (summary or '').

#5
provider refusal

Refused by the provider (too short) — status refused, terminal, zero retries; distinct from error, which retries.

✺ · Synthesis

The verdict machine

The stage is a persistent verdict machine: score once — the DB row is the cache — and verdict = policy(score, config threshold). States are pending / relevant / irrelevant / refused (terminal) / error (retryable). It needs the fetcher to also store the RSS summary. The report mirrors the fetcher's pattern and aggregates usage. Threshold is global, default 0.7.
