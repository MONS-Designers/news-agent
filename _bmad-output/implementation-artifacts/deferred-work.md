## Deferred from: intent clarification for LLM-backed Role/Topic/Prompt suggestion wiring (2026-07-28)

- source_spec: none
  summary: Wire real Topic suggestions with support for brand-new (not-yet-curated) Topic names the LLM invents, distinct from Role's "Other" flow because Topic selection is a hard FK (`UserTopicPreference.topic_id`) rather than a free string.
  evidence: Confirmed design in conversation with the user (not yet spec'd): add a `status` column to `Topic` (pending/approved/rejected, mirroring `Source.status`'s existing shape). Selecting an LLM-invented new Topic creates a real `Topic` row immediately with `status='pending'` plus a real `UserTopicPreference` for that user right away (counts toward their cap, fully functional for that user immediately — unlike Field/Role's `PendingTaxonomySuggestion`, which defers row creation until admin promotion). Only `status='approved'` Topics are offered as suggestion candidates to *other* users. Admin approving flips status to `approved` (now suggestible to others); admin rejecting flips it to `rejected` and it stays stuck there permanently — still fully functional for the original selecting user, never offered to anyone else again. Needs: Alembic migration (existing Topics default `approved`), `services/sources.py` changes (`add_topic` gains a status param), a new service function mirroring `set_source_status` for topics, an admin approve/reject endpoint + UI (new, or extend the existing Taxonomy Curation Queue), and `suggest_topics`'s candidate list (`_topic_popularity` in `services/profile.py`) filtered to `approved` only plus now carrying `Topic.name` (today it's `topic_id`+`selection_count` only, no name — the LLM can't reason about topics it can't see the name of).

## Deferred from: code review of story-1.1 (2026-07-26)

- **No `GET /me/profile`; picker state dies on unmount.** `FieldStep` owns `selectedName`/`isOther`/`otherText` and is destroyed by `v-if`, and there is no read endpoint to rehydrate a saved `field_name`. A returning user sees a blank picker with no sign anything was saved; clicking Reload mid-entry silently discards typed input. Story 1.3's acceptance criterion ("Given I click Back from Step 2 … my previously selected Field/Role/Experience still show as selected") requires lifting this state into the shell plus a read path — that story owns the fix.
- **No Back navigation.** Clicking Continue advances to placeholder steps 2/3 with no way back short of a page reload. EXPERIENCE.md § Component Patterns requires Back on every step, always available and never gated, but steps 2/3 are intentional stubs in Story 1.1 — Back becomes meaningful when Story 1.4 builds Step 2.
- **Not responsive.** No media queries in either picker component; the three-item `flex: 1` stepper with `white-space: nowrap` labels overflows below ~375px, and nested 30px paddings compound on narrow viewports. Tracked as news-agent#30.
- **`add_field` TOCTOU race.** SELECT-then-INSERT against the unique `ix_fields_name`, committing once per field, so a concurrent seeder's loser raises an uncaught `IntegrityError` and aborts `seed_default_fields` mid-loop with a failed session. Pre-existing pattern: faithfully mirrors `add_topic`/`add_source` in `services/sources.py`. Worth fixing project-wide rather than in one story.
- **Editable install points at a stale worktree.** `pip show newsagent` resolves to `C:\project\news-agent\.claude\worktrees\github-issues-review-6e1f99`, so `python -m newsagent.cli` and `alembic` run another branch's code unless `PYTHONPATH=src` is set explicitly. Pre-existing environment issue, not caused by this change, but it will bite anyone running migrations from a plain shell.

## Deferred from: code review of spec-role-and-prompt-suggestions (2026-07-28)

- source_spec: `_bmad-output/implementation-artifacts/spec-role-and-prompt-suggestions.md`
  summary: The Role picker's `GET /me/fields/{field_id}/roles` fetch is a synchronous, in-request LLM call with worst-case ~90s of blocked FastAPI worker time (3 retries × 30s HTTP timeout + backoff) and no client-side abort/timeout, so a slow or hanging local LLM stalls Step 1 of the profile wizard.
  evidence: `suggestions/base.py`'s `_run` retries transient `SuggestionError`s up to 3 times with exponential backoff; `http_llm_client.py` defaults each attempt to a 30s timeout; `frontend/src/api/client.ts`'s `request()` has no `AbortController`. This is an emergent consequence of the story's own explicit "synchronously" / "no streaming or async" constraint, so it isn't this story's fix to make — worth a deliberate revisit (background polling, a shorter timeout, or a client-side abort) once a real local LLM is wired into a user-facing environment.
- source_spec: `_bmad-output/implementation-artifacts/spec-role-and-prompt-suggestions.md`
  summary: `services/taxonomy.py::suggest_roles_for_field` and `services/profile.py::suggest_prompts_for_user` only catch `SuggestionError`; a misconfigured provider (`get_suggestion_source()` raising `ValueError` for an unknown `NEWSAGENT_SUGGESTION_PROVIDER`, or an unconfigured `LOCAL_LLM_BASE_URL`/`LOCAL_LLM_MODEL`) propagates as an uncaught 500 instead of the "never blocks Role selection / no error shown" fallback the story promises.
  evidence: `suggestions/factory.py::get_suggestion_source` and `LLMSuggestionSource.__init__` both raise plain `ValueError` on misconfiguration, and it happens inside the `try: ... except SuggestionError` block in both new call sites. The same gap already exists in `_compute_and_store_suggestions` (pre-existing, but silent there since it's a `BackgroundTask`) — this story just adds two new *synchronous* call sites where it reaches the user as a 500. A systemic fix (base `SuggestionSource` config validated at startup, or `get_suggestion_source()` mapping config errors to `SuggestionError`) is out of scope for this story.
